# 浏览器下载接管设计 · #2521

2026-11-19 的[竞品调研与跨仓实施方案](takeover-cross-repo-plan.zh-CN.md)给出了六款下载工具的接管顺序、现有 MDXP PR、兼容发布步骤和跨仓验收。本文保留问题诊断、浏览器实验与设计细节。

建议先交付一个用户能验证的承诺：在“下载前询问”模式下，打开确认框时，浏览器要么尚未发起文件请求，要么原下载项已核实暂停。两者都做不到时，让浏览器完成下载。保留用户修改文件名和 Motrix 保存目录的机会；同一次选择只交给一个下载器。

## 诊断与实测

报告环境为 macOS 27.0.1、Motrix 2.4.1，未注明扩展版本或文件地址。分析基线为扩展 v0.1.23，本地 main `55393c8` 与该标签的生产源码和 manifest 相同。Brave 用户还报告，启用浏览器自己的“每次询问保存位置”时，原生保存框会抢在扩展弹窗前出现。这两个开关需要分别验收。[Motrix #2521](https://github.com/agalwood/Motrix/issues/2521) · [扩展 #55](https://github.com/motrixapp/motrix-extension/issues/55)

| 路径 | 当前行为 | 后果 |
| --- | --- | --- |
| Chromium 确认模式 | `onDeterminingFilename` 收到已有的 DownloadItem；`handleHeld` 调用 `hold.release()` 后才进入 `confirmInterceptedDownload`。确认草稿未携带原下载 ID，提交动作也没有取消原任务。 | 用户还在编辑时 Chrome 就可以写完整个文件；点击“添加”可再创建独立的 Motrix 任务。现有 Chromium 单测明确要求这一顺序。 |
| Firefox 提前接管命中 | `onHeadersReceived` 在有界预检后返回 `{cancel:true}`，随后异步询问。收到响应头意味着源站已收到第一次请求。 | 确认时无原生下载项；选择浏览器会重新 GET，一次性 URL 可能已经消耗。 |
| Firefox 提前接管未命中或关闭 | 符合后续条件的 DownloadItem 进入 `downloads.onCreated` 适配器，同样使用保留原任务的确认逻辑。 | 同一浏览器也可能表现不同。 |

源码入口见 [Chromium 适配器](../src/background/interception/chromium.ts)、[确认提交动作](../src/background/confirmedDownload.ts)、[Firefox 提前接管](../src/background/interception/webRequestEarly.ts) 和 [Firefox 下载项适配器](../src/background/interception/firefox.ts)。

**Chromium 对照实验。** 在临时 profile 中加载打包后的生产 Chromium 拦截模块，本地 HTTP 服务每 65 ms 发送 64 KiB，总计 4 MiB。开启确认模式，用一直待定的确认回调模拟用户停留；使用浏览器默认下载处理，关闭浏览器的保存位置询问。Chrome for Testing 159.0.8154.6 的结果如下。

| 场景 | 确认后 2 秒 | 确认后 5 秒 | 结果 |
| --- | ---: | ---: | --- |
| 当前生产适配器 | 1,507,328 B | 4,194,304 B | 已完成，临时目录中出现文件 |
| 确认回调触发后对该 ID 调用 pause | 0 B | 0 B | 两次读取均为 paused；取消后目录中无该文件 |
| 在独立运行中重复暂停，再 resume 同一 ID | 0 B | 0 B | 同一 ID 完成 4 MiB，源站共收到 1 次 GET |

数值来自 `downloads.search` 的 `bytesReceived`。即使该值是 0，三次实验的源站也都收到了初始 GET。暂停可以制止持续下载；请求、网络缓冲、临时文件或原生保存框仍可能先出现。本实验替换了确认 UI 和连接依赖，没有启动 Motrix 引擎。[Chrome downloads API](https://developer.chrome.com/docs/extensions/reference/api/downloads)

**Firefox 对照。** 仓库的 Firefox 157.0 真浏览器用例使用本地 HTTP 和 MDXP 模拟器。提前接管命中后，等待确认时原生下载项为 0。选择 Motrix 产生 1 个模拟任务，源站记录 1 个来自浏览器的 GET；选择浏览器产生 0 个模拟任务，源站记录 2 个 GET；显式取消产生 0 个任务，源站仍记录 1 个 GET。模拟器不下载文件。本次执行通过 22 个 Firefox 场景和 119 项相关单测。[验收脚本与覆盖范围](takeover-ci-acceptance.md)

## 单次下载链接的保留条件

以“首次文件 GET 成功后，同一令牌的任何后续请求均返回 403/410”为例。Chromium 现有确认路径保留首次响应，即使 Motrix 再取失败，浏览器仍有机会下完。Firefox 提前取消路径会丢掉这条响应。MDXP 的 taskId 只证明已建任务；源站是否接受请求、响应是否为目标文件、下载最终能否完成，是另外三个事实。[当前行为说明](../README.zh-CN.md) · [原响应保护的回归用例](../src/background/interception/__tests__/chromium.test.ts)

**裁决顺序。** 如果文件请求已经发出，只有站点提供明确的可重复下载约定，或有经过验证、能为 Motrix 独立签发新授权的站点适配时，才考虑自动交接。其余情况（含来源不明、只知道是 GET、签名语义不明、令牌可能绑定 Cookie／IP）一律让原项继续到结束。无需暂停、探测或提交，也无需预先认出每一家网盘。暂停中的连接可能被源站关闭，恢复同一 ID 仍可能需要新 GET 或 Range；保持原响应连续读取对这类文件更稳妥。此规则在响应头取消、元数据探测和下载项暂停之前执行。若未来覆盖直接模式，同样前置此判断。

如果能在首个文件请求前确认，选择浏览器就让浏览器独占首次请求；选择 Motrix 只有在链接、必要授权及端点身份可等价传递时才适合。严格一次请求的来源还要求引擎可禁用探测、并发分片及自动重试，让第一个请求直接接收并写入文件。不能证明当前端点具备这些能力时，自动路径留给浏览器。换取新链接需要服务方支持。幂等键解决重复建任务，无法恢复源站已经消费的令牌。

### 官网维护网盘保护名单

建议由 `motrix-website` 维护公开的“优先使用浏览器下载”名单，供 Chrome 和 Firefox 共用。首版仅提供一种条目语义：命中后让网页和浏览器完成自动下载流程。扩展应在点击拦截、Firefox 响应头取消、探测和暂停之前检查。未命中时继续使用上节的判定，因此漏收新网盘也不会把未知链接升级为可重放。用户主动右键发送仍是独立入口，适用原有授权与单次下载条件。

每条记录指定精确主机，可选路径前缀，明确匹配来源页还是下载地址。只有服务方独占的命名空间才扩大到子域。一次下载已匹配网盘来源页或原始下载地址，后续跳转到 CDN 时继续保留保护；直接打开共享 CDN 地址且来源不明时，执行未知来源策略。来源缺失就保留为未知，不能把回填的下载 URL 当成真实来源证据。用户自己的站点排除与官网保护名单取并集。若某网盘的一条下载路径经验证支持 Motrix，可随扩展发布对应支持并注明授权、请求次数和适用端点，官网加入域名本身不授予接管能力。

发布建议：单一 JSON 源文件经过 PR 审核，条目附公开问题或复现依据；CI 检查 schema、域名边界和匹配／不匹配样例。网站发布静态文件（建议路径 `/rules/download-protection/v1.json`），扩展发布时从同源数据打包一份快照。运行时定期使用 ETag 更新，本地完成所有匹配，访问网盘时不向官网发送页面地址、文件链接或 Cookie。首次离线使用内置快照，更新失败或格式不兼容时沿用最近有效版本。匹配代码及固定动作随扩展发布，远端只传域名和路径等数据。[Chrome 远程代码与数据说明](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code)

## 用户如何选择

IDM 用文件类型和站点例外控制自动接管，用户也能按键临时放行，或右键明确交给 IDM。Gopeed 同样提供独立的右键下载入口，并支持选择远端下载器。Motrix 可沿用已有的规则、右键菜单和目标端点，把“这次用谁下载”放在一次点击内。Chrome 商店常规安装的 MV3 扩展受到阻塞式 webRequest 权限限制，不能直接套用 Firefox 的响应取消方案。[IDM 接管与按键](https://www.internetdownloadmanager.com/support/using_idm/starting.html) · [IDM 文件与站点规则](https://www.internetdownloadmanager.com/support/using_idm/options.html) · [Gopeed 扩展](https://github.com/GopeedLab/browser-extension) · [Chrome webRequest](https://developer.chrome.com/docs/extensions/reference/api/webRequest)

保留“自动接管”总开关、已有的“直接下载／下载前询问”、规则顺序、未知大小策略及目录设置。改动先作用于确认模式。弹窗显示文件名、保存目录、当前 Motrix 端点，以及与本次操作相符的状态（“尚未开始下载”或“浏览器下载已暂停”）。主操作“用 Motrix 下载”，次操作“用浏览器下载”，单独提供“取消此次下载”。右键继续作为显式入口；对允许识别的普通点击，可加入单次“用浏览器”快捷键，按平台避开系统和浏览器默认手势。

## 按最早能确定下载意图的位置处理

**Chrome 的两个介入点。** 对可识别且可等价处理的链接，在 `document_start` 注册捕获阶段的 `click` 监听器，在可取消的可信点击中同步调用 `preventDefault()`，再异步询问。这个动作仅阻止链接的默认行为，网页脚本独立发起的 fetch、表单或导航仍可运行。对仅从响应头识别的附件，在 `downloads.onCreated` 取得原下载 ID；只有当时已有可重放依据且规则命中时才暂停。文件名或大小尚缺且会影响判断时放行。`onDeterminingFilename` 可按同一 ID 补充建议文件名，及时返回，避免同一下载弹两次确认。[Chrome 内容脚本](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts) · [Chrome 下载事件](https://developer.chrome.com/docs/extensions/reference/api/downloads#events)

本地最小 MV3 扩展与 Chrome for Testing 159.0.8154.6 的单次 GET 实验中，同源 `<a download>` 的默认点击被拦下时，源站文件 GET 数为 0。另一条无后缀附件链接的实测顺序为 `onBeforeRequest → onHeadersReceived → onCreated → pause 成功 → onDeterminingFilename`。创建时文件名为空、已收字节为 0，但源站已收到 1 个 GET；文件名事件才提供 `sample.bin`。此次恢复同一 ID 完成 2 MiB，源站只收到 1 个 GET。该实验使用临时 profile 和本地限速源；实现不能依赖不同监听器异步工作的完成顺序。

常规商店 MV3 扩展可以用 `webRequest.onBeforeRequest` 观察请求；阻塞式监听只对策略安装的扩展开放。DNR 的预设规则可以在请求前匹配已知 URL 并阻止或重定向；依据 `Content-Disposition` 匹配的规则在源站收到请求后才生效。这些规则都不能挂起首次请求、弹窗后再原样放行。[Chrome webRequest](https://developer.chrome.com/docs/extensions/reference/api/webRequest#permissions) · [DNR 规则生效时机](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest#rule-evaluation)

| 入口 | 何时采用 | 确认前及放行行为 |
| --- | --- | --- |
| 普通 HTTP(S) 下载直链，或明确的右键下载 | 对普通点击，仅处理可信用户激活、页面允许注入、下载意图明确且规则能在请求前决定的链接，例如同源带 `download` 的锚点。显式右键沿用自己的策略。 | 点击时同步阻止默认导航，之后异步显示确认，不做 HEAD 或 Range 探测。浏览器选择只触发一次与原意等价的下载，保留文件名、来源页及浏览上下文。无法保证等价的点击留给页面。 |
| 已创建的 Chromium 或 Firefox 下载项 | 仅限符合上节可重放条件的响应头附件、无扩展名资源等。先应用站点、大小及端点规则。 | 以原 `downloadId` 暂停，并查询确认仍为进行中且已暂停，再展示表单。Chromium 的 `suggest()` 只承担文件名决议，及时释放，不能持有它等待人操作。放行用同一 ID 的 resume。 |
| Firefox 响应头入口 | 确认模式遇到未被点击入口处理的附件。 | 让原响应继续。仅明确可重放的资源进入下载项暂停路径。可独立保留和回滚现有直接模式的提前取消优化。只有点击入口能在文件首个 GET 前作决定。 |
| 网页专属下载 | POST 导出、Blob/Data URL、已知一次性链接、已有浏览器预览意图、身份上下文无法等价传递，或权限不足。 | 保留浏览器所有权。晚发现的 GET 需有原方法与上下文的可信证据；文件名后缀或相同 MIME 无法证明可重放。无可靠请求关联时放行。 |

普通点击入口建议先小范围启用。按标签页和 frame 缓存只读策略快照；快照过期、快捷键放行、站点排除、网页自定义动作、修饰键导航、沙箱或下载属性语义不明确时，让浏览器照常处理。命中后后台重新校验设置、来源和端点。创建操作前检查未知大小策略；大小是必要条件时延后到下载项入口。避免按 URL 设全局短时去重：同一地址两次主动下载应得到两个操作。浏览器回退通过自身扩展发起标记，或单次可关联的放行凭据穿过后续入口；无法可靠关联的网页动作不参与提前接管。

晚接管的请求关联是首版验证点。Chromium DownloadItem 没有 webRequest 的 requestId；可短时记录原请求的方法、来源、重定向链及响应类型，仅在与下载项唯一匹配时采用。关联成功只能识别首次请求；自动交接还必须满足“单次下载链接的保留条件”中的要求。同 URL 并发或关联不明时放行。即使确认是 GET，令牌能否再次使用仍由源站决定；已知依赖会话或一次性授权的站点应保留浏览器原项。向远端 Motrix Server 提交时继续执行现有的端点配对、自动接管授权和敏感数据同意检查。

## 第一版交接顺序

下表的“已暂停原下载项”只适用于已确认可重放的来源。对于补签方案，须先获得独立可用的新授权；获取失败即交还原下载。第一版使用现有 MDXP `download/submit` 和操作幂等键。原生下载项以“在我暂停的这个 ID 上能做什么”为准；已由用户暂停的项目留给用户。暂停前登记操作，记录 `operationId`、浏览器下载 ID、端点 ID 与 revision、阶段和期限。提交前持久记录“可能已经发出”；跨普通／隐身上下文隔离恢复记录，Cookie 和鉴权头不得进入恢复日志。改造现有确认服务与提交服务，共用同一操作键和提交结果。[确认服务](../src/background/DownloadConfirmationService.ts) · [提交服务](../src/background/DownloadSubmissionService.ts)

| 事件 | 尚无浏览器请求 | 已暂停原下载项 |
| --- | --- | --- |
| 选 Motrix | 校验当前端点和选项，提交一次 | 再读原项，确认仍由扩展暂停；保持暂停并提交。收到有效 taskId 后取消同一 ID，核对终态，再显示交接成功。 |
| 选浏览器 | 依原上下文启动一次 | 恢复同一 ID，核对状态；续传和服务器是否支持 Range 由浏览器决定。 |
| 明确点“取消此次下载” | 结束操作 | 取消同一 ID 并核对终态。 |
| 提交前关闭、超时、弹窗无法打开、配置关闭或端点变更 | 自动点击入口将原意交还浏览器一次；显式右键关闭则结束 | 只恢复由本次操作暂停的原项。用户已取消、恢复或完成时尊重浏览器现状。 |
| 提交明确被拒绝 | 告知失败，提供“用浏览器下载” | 恢复原项并显示失败原因。 |
| 提交已发出，回应丢失或后台重启时结果未知 | 展示“请核对 Motrix 任务”，保留操作号 | 保持暂停，提供“查看 Motrix 任务”和带重复风险提示的手动恢复。超时或关闭弹窗不能触发回退。 |

三个竞争条件直接决定能否上线：

1. **小文件已完成或 pause 失败。** 查询原项；已完成、被用户取消或无法确认暂停时，结束自动接管，不提交。若暂停操作可能已生效，先对账并释放本次暂停，避免遗留任务。浏览器原文件始终由用户处理。
2. **已取得 taskId，但原项取消失败。** Chrome 文档指出 `cancel` 完成回调可能对应已完成、已中断或已不存在的项目。核对 ID、下载状态和中断原因；取消失败且仍暂停时保留 taskId，允许重试清理；原文件已经完成时如实提示。仅在已证实本次取消后按需擦除历史。清理失败不能重提任务或删除已完成文件。[Chrome downloads.cancel](https://developer.chrome.com/docs/extensions/reference/api/downloads#method-cancel)
3. **两个下载或两个决策并发。** 每个操作单独结算，同一窗口排队显示；关闭窗口不能让另一个下载失去恢复动作。浏览器状态事件、弹窗按钮、过期回调和 worker 恢复均通过同一个阶段检查。恢复时先查询原 ID 和原端点的提交记录；已接受只重试清理，未发出才允许释放，未知则留待核对。旧草稿缺少原 ID 时不按 URL 猜测所有权。

第一版仍有“服务端已经接受、浏览器清理尚未完成”的窗口。需要无人值守地解决丢回执时，再在 MDXP 协商可选的 prepare／commit／status／abort 能力。prepare 只保存有期限的意向并校验目录，commit 才可启动下载；服务端以端点与操作键记账，重复 commit 返回同一任务，abort 与 commit 只有一个终态。原下载停止前失败可恢复原项；原下载已停止后失败只能对账并按可重放性提供恢复选择。旧端点继续使用上述确认流程。协议握手或 taskId 都不能证明源站会接受第二次 GET。

## 实施和验收

1. **先修 #2521 的持续传输和 #55 的重复文件。** 修改 Chromium／Firefox 原生适配器、确认草稿和确认动作，引入按 ID 恢复、取消及未知结果处理。将 Firefox 确认模式从提前取消切至下载项处理；直接模式单独回归。Safari 当前没有自动下载接管能力，维持显式入口。此版验收“确认期间原项已暂停”，文件请求可早于表单。
2. **再覆盖请求前可识别的下载。** 接入普通点击、站点／类型规则和单次放行；同一确认服务处理右键与自动点击。经过允许的直链验收“确认前文件 GET 为 0”。浏览器原生“询问保存位置”开启时，直链选 Motrix 不应触发原生保存框；晚接管场景单列实际结果。
3. **用真实浏览器验证归属。** 至少覆盖 Chrome 与 Brave、Firefox 提前入口及降级路径，在 macOS、Windows 验证保存位置开／关。分别记录确认框、原下载 ID／字节／终态、源站 GET／Range，以及 MDXP 操作键和任务数。用固定大小文件校验浏览器最终文件；以真实 Motrix 另测一次最终文件及摘要，区分“服务端接受”和“文件下载成功”。

| 发布用例 | 通过条件 |
| --- | --- |
| 明确可重放的慢速附件、用户停留超过现有 12 秒文件名保护期限 | 展示确认时原项已暂停，稳定后字节不再增长，Motrix 任务数为 0；选择 Motrix 后只接受一个任务，原项未完成。 |
| 瞬时小文件、无法暂停或已被用户完成 | 浏览器一份完成文件；无自动 Motrix 任务。 |
| 直链的 Motrix／浏览器／取消 | 确认前文件 GET 为 0；选 Motrix 只由 Motrix 发起下载；选浏览器一次，显式取消零份。 |
| 严格单次 GET，首次返回文件，后续 GET／Range 返回 410；另测中途暂停会断开的慢速源 | 晚发现时浏览器连续完成，文件摘要正确，源站只收到首次文件 GET；扩展 pause、cancel、探测及 MDXP 提交次数全为 0。Chrome 与 Firefox 分别验证。 |
| 请求前可判断的单次直链 | 若宣称支持 Motrix，使用真实引擎验证源站只收到一次文件 GET、无探测／分片／重试且文件摘要正确。覆盖令牌过期和远端身份不匹配；不具备条件时由浏览器处理。 |
| 不可重放、排除站点、跨站重定向、未知大小、内联 PDF | 保留原请求与预览行为，策略需要的信息不足时放行；无额外探测消耗令牌。 |
| 双击提交、同 URL 两个下载、丢回执、弹窗关闭、worker 重启、端点切换 | 同操作最多一个 Motrix 任务，独立操作互不影响；既无自动重复 GET，也无静默遗留的暂停项。 |
| 浏览器保存框、后台窗口、连接或权限不可用 | 实测原生框和扩展表单出现顺序；未获得原项控制权时由浏览器继续。 |
